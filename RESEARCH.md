### 1. The spec moved: 2026-07-28 is current, and it is a redesign

Revisions since the widely-known 2025-06-18 spec: `2025-11-25`, then `2026-07-28` (current). The second is breaking in shape, with a 12-month deprecation window under a new formal feature-lifecycle policy.

What changed that matters here:

| Change | Consequence for Commonwealth |
|---|---|
| Protocol is now stateless: no `initialize` handshake, no `Mcp-Session-Id`; version/capabilities ride in `_meta` per request; new `server/discover` RPC (SEP-2575, SEP-2567) | Hosted deployment gets much simpler: any replica answers any request, no session affinity. Public read-only servers are the best case for this model. Design servers stateless from day one; cross-call state (cursors, cached result handles) must be explicit server-minted handles passed as tool arguments, which is exactly how the result-resource pattern already works. |
| `ttlMs` and `cacheScope` now required on list/read results (SEP-2549); ETags for tool results on the roadmap | Scope matters (correction 2026-08-26, second review round): these fields attach to `tools/list`, `resources/read`, and peers — **not to ordinary `tools/call` results** — so tool-result freshness stays a Commonwealth-envelope job. The protocol hints apply to result *resources* and catalogs: manifests' cadence maps to `ttlMs` there, with `cacheScope: "public"` for the public surface. |
| Servers SHOULD return `tools/list` in deterministic order (prompt-cache friendliness) | Trivial to comply, easy to get wrong with dict-ordered registries. Make tool ordering a contract test. |
| Sampling, Roots, and Logging deprecated (SEP-2577); server-initiated requests replaced by MRTR: server returns `resultType: "input_required"` with `inputRequests`, client retries with `inputResponses` (SEP-2322) | Do not design anything on sampling/roots/logging. Ambiguity handling (jurisdiction disambiguation) has two viable shapes: return candidates in `data` (portable everywhere) or MRTR input-required (protocol-blessed, newer clients). Decision record DECISIONS.md 0004 covers the choice. |
| Tasks are an official extension (`io.modelcontextprotocol/tasks`), polling-based (SEP-2663) | Long-running work (bulk exports, big spatial scans) has a sanctioned pattern; V1 mostly won't need it, Phase 2+ bulk tooling should use the extension rather than inventing job tools. |
| SSE resumability removed; HTTP+SSE transport formally deprecated | Matches the design spec's existing "no new SSE" stance. A dropped stream means re-issue the request; idempotent read tools make that free. |
| Dynamic Client Registration deprecated in favor of Client ID Metadata Documents; `iss` validation required; per-issuer credential keying | Affects Phase 5 (authenticated tiers) only, but write the auth spec against CIMD + EMA, not DCR. |
| OpenTelemetry trace-context conventions for `_meta`; per-request log level | The observability section of the design spec should adopt OTel conventions instead of a bespoke logging story. |

Roadmap items to watch (not shipped): server-side "progressive discovery" (clients learn tools on demand — would partially obsolete client-side tool search), HTTP-over-stdio transport unification, `tools/call` result-shape redesign by the new Core Primitives WG, DPoP and workload-identity work. None are stable enough to build against; progressive discovery is the one to track because it lands exactly on Commonwealth's toolset-exposure problem.

### 2. Governance: donated, foundation-run, SEP-driven

Anthropic donated MCP to the Agentic AI Foundation under the Linux Foundation in December 2025 (announcement discussed at [HN 46207425](https://news.ycombinator.com/item?id=46207425); Google's A2A protocol sits in the same foundation). Day-to-day: named core maintainers per roadmap area, working groups (Transports, Core Primitives forming, Agent Identity forming, File Uploads, SDK), and a PR-based SEP process where every substantive change carries a SEP number. Practical consequence: the protocol is no longer a single-vendor bet, changes are trackable by watching SEPs, and proposals aligned with a roadmap area get expedited review. If Commonwealth ever needs a protocol accommodation (unlikely), the path exists.

### 3. Registry: real, preview, aggregator-shaped

- registry.modelcontextprotocol.io is in preview ("breaking changes or data resets may occur"), API frozen at `/v0.1`. Backed by Anthropic, GitHub, PulseMCP, Microsoft.
- It is a metadata catalog, not a package host: `server.json` (schema version 2025-12-11, its own versioning track) points at npm/PyPI/OCI/NuGet/MCPB packages or remote URLs.
- Namespacing is verified reverse-DNS: `io.github.<user>/<name>` via GitHub auth, or `com.example/<name>` via DNS challenge. Publishing runs through the `mcp-publisher` CLI.
- The intended consumers are downstream aggregators (GitHub MCP Registry, Smithery, and peers) that pull hourly and layer curation; hosts consume aggregators, not the registry.
- Our snapshot (`research/raw/registry/`): 20,000+ servers (crawl capped), 14,201 with remote endpoints, streamable-http outnumbering SSE 13,980 to 864, packages led by npm (5,057) and PyPI (3,817). Civic-keyword matches are commercial noise; no state government publishes there yet.

**For Commonwealth:** register a DNS-verified namespace (e.g. `org.commonwealthmcp/*` or the project domain) early; publish every public server there with accurate metadata; expect discovery to actually happen through aggregators and through the project's own docs. The registry's noise level makes Commonwealth's authority signals (agency linkage, provenance discipline) the differentiator, and the "subregistry" OpenAPI spec is the path if Virginia agencies ever want a government-scoped registry view.

### 4. Anthropic's tool-design guidance now carries numbers

From "Writing tools for agents" (2025-09), the tool-search docs, and "Code execution with MCP" (2025-11):

- ~55K tokens of tool definitions is a typical multi-server setup's dead weight; selection accuracy degrades past 30-50 tools regardless of budget. Tool search (regex or BM25 variants, `defer_loading`) cuts context by >85% and holds accuracy by loading ~3-5 tools per request; deferred tools preserve prompt caching.
- Code execution over MCP cut one workflow 150K→2K tokens (98.7%); the cost is a sandbox you must operate.
- Concise vs. detailed response modes: a Slack example dropped 206→72 tokens. Claude Code caps tool results at 25K tokens.
- Namespaced tool names measurably affect selection; semantic identifiers beat UUIDs in retrieval precision; error messages should tell the model what to do next; description refinement alone produced SWE-bench-visible gains.

**For Commonwealth:** the design spec's semantic-tool bet is confirmed by the vendor's own data. Adopt concretely: `concise`/`detailed` response modes on every read tool (concise default), 25K hard ceiling with the envelope's own ~2K target, namespaced tool names (`geo.*`, `civic.*`), deterministic ordering, and treat descriptions as versioned, eval-covered artifacts.

### 5. Skills are a vendor-neutral spec with an MCP bridge

Agent Skills now lives at agentskills.io as a cross-vendor spec (the Anthropic repo points there). Constraints that matter for Commonwealth Skills packaging: `name` ≤64 chars matching the directory, `description` ≤1024 chars covering what AND when, body under ~500 lines with references one level deep, three-stage progressive disclosure (~100 tokens of metadata always loaded; body on activation; resources on demand), experimental `allowed-tools` field, and a validator CLI (`skills-ref validate`). An official "Skills over MCP" extension (discovery/serving of skills through MCP) exists with a working group; mechanics unverified.

**For Commonwealth:** package Commonwealth Skills to the agentskills.io spec verbatim so they run on any compliant host, and track Skills-over-MCP as the eventual distribution channel (a Commonwealth server advertising its own workflow skills would collapse the install story).

### 6. SDK landscape: names collide, pick deliberately

- Official Python SDK: v2.x (2.0.0 shipped the day of the spec revision; 2.1.1 current). Backward-compatible dual-era serving (2025-11-25 and 2026-07-28 clients simultaneously). Breaking rename inside it: the high-level class formerly imported as `FastMCP` is now `MCPServer`; v1 code migrating naively breaks.
- Standalone FastMCP (jlowin, gofastmcp.com): 3.4.7 stable, 4.0 in beta; the larger-framework option (auth providers, middleware, composition); whether released versions fully speak 2026-07-28 was not verifiable at research time.
- TypeScript SDK v2 tracks the new spec (stable status unverified at research time).

**For Commonwealth:** this is a real decision with a decision record (DECISIONS.md 0003): official SDK v2 (spec-tracking, minimal) vs standalone FastMCP 3.x/4.x (batteries, its own cadence). Whatever is chosen, pin exactly and never write the unqualified word "FastMCP" in docs without saying which one.

### 7. MCP Apps shipped; client feature matrices are extension-shaped now

MCP Apps (`io.modelcontextprotocol/ui`, spec dated 2026-01-26) renders sandboxed interactive UI inside tool results and is supported across Claude web/Desktop, ChatGPT, Cursor, VS Code Copilot, M365 Copilot, Goose, Postman, and others. Enterprise-Managed Authorization is a stable extension with thin client support so far. A maintained core-primitive-by-client matrix effectively no longer exists; the community matrix tracks extensions, because core tools/resources/prompts support is near-universal and the deprecated trio is being phased out anyway.

**For Commonwealth:** a map view or evidence table rendered via MCP Apps is a credible Phase 2+ enhancement (zoning maps beg for it), but nothing in V1 should require it. Rely on: tools, resources, structured output. Treat elicitation/MRTR as progressive enhancement. Do not build on sampling, roots, or protocol logging.

### 1. Executive Summary

The repositories reviewed do not represent one architecture with small implementation differences. They optimize for different layers of an agent-tool ecosystem.

The most useful framing is:

| Project / Pattern | Primary question it answers |
|---|---|
| PNNL `nepa-mcp` | How should authoritative government-data MCP servers be built and composed? |
| Power-Agent | How should raw tools, canonical representations, expert workflows, and benchmarks be separated? |
| GSA MCP Server Hub Catalog | How should many MCP servers be discovered, deployed, credentialed, isolated, and governed? |
| GitHub MCP | How should a very large tool surface be selectively exposed to agents? |
| Cloudflare domain MCPs | When should capabilities be split into typed, domain-specific servers? |
| Cloudflare Code Mode | How can thousands of API endpoints be exposed with minimal schema/context cost? |
| Context7 | How small can an MCP discovery/retrieval surface be? |
| AWS MCP / Agent Toolkit | How should production identity, authorization, audit, and evaluated workflows work? |
| Playwright MCP / CLI+Skills | When should a capability use MCP versus CLI + skills? |
| Official MCP reference servers | What does a minimal standards-compliant MCP implementation look like? |

For Commonwealth-MCP, the recommended weighting is:

| Reference | Long-run architectural influence |
|---|---:|
| PNNL NEPA-MCP | 25% |
| Power-Agent | 25% |
| GSA MCP Hub | 18% |
| GitHub MCP | 12% |
| Cloudflare | 10% |
| AWS | 5% |
| Context7 | 3% |
| Playwright / CLI | 2% |

This weighting is not a quality ranking. It reflects relevance to Commonwealth's goals:
- 133 Virginia counties/independent cities,
- many state and local agencies,
- heterogeneous systems,
- strong geospatial needs,
- public-data-first,
- mostly read-only,
- cross-source joins,
- open-source contributions,
- eventual hosted multi-user operation,
- possible portability to other states.

### 3. PNNL `nepa-mcp`

**Repository:** https://github.com/pnnl/nepa-mcp

#### 3.1 Observed Architecture

PNNL's NEPA MCP toolkit is a family of environmental and regulatory MCP servers built around public authoritative data sources.

Observed characteristics:
- many separate MCP servers,
- dozens of tools,
- shared common runtime utilities,
- common HTTP/validation/GIS helpers,
- strongly domain-specific tools,
- a cross-server `nepa-screening` skill,
- a `map_composer` server for cross-source geospatial composition,
- explicit treatment of partial failures and source coverage,
- installer/doctor/configuration tooling,
- plugin packaging.

Representative per-domain layout:

```text
server_name/
├── requirements.txt
├── server.py
└── src/
    ├── apis/
    └── core/
```

Shared code lives outside the individual servers.

#### 3.2 Architectural Philosophy

The fundamental pattern is:

```text
authoritative source
    ↓
specialized API wrapper
    ↓
domain-aware MCP tools
    ↓
skill-level workflow composition
```

It places considerable emphasis on:
- authoritative source selection,
- screening limitations,
- coverage warnings,
- source-specific semantics.

#### 3.3 Strengths for Commonwealth

##### Very high
- Government/public-data analog.
- Geospatial workflows.
- Provenance and coverage.
- Domain-specific typed tools.
- Shared infrastructure across many sources.
- Skills that distinguish data retrieval from expert interpretation.
- Clear warnings against turning screening results into legal determinations.

##### Especially relevant pattern

The `nepa-screening` skill chooses different authoritative systems for:
- Census,
- IPaC,
- FEMA,
- EPA,
- protected lands,
- regulatory research,
- cultural resources.

This is structurally similar to Commonwealth workflows where one task may require:
- VGIN,
- locality GIS,
- DEQ,
- VDOT,
- LIS,
- public meetings,
- procurement.

#### 3.4 Weaknesses for Commonwealth

The largest issue is **server granularity**.

A federal NEPA domain has a bounded number of major publishers.

Virginia contains:
- state agencies,
- 95 counties,
- 38 independent cities,
- school divisions,
- constitutional offices,
- regional agencies,
- transit operators,
- thousands of local GIS layers.

A literal PNNL pattern could become:

```text
mcp-fairfax
mcp-loudoun
mcp-richmond
mcp-arlington
...
```

This does not scale.

#### 3.5 What to Copy

Copy:
- shared common package,
- domain semantics,
- authoritative-source discipline,
- GIS conventions,
- provenance,
- coverage warnings,
- partial-source behavior,
- cross-server skills,
- installer/doctor patterns.

Do not copy:
- default assumption that a source/publisher should be its own server.

#### 3.6 Commonwealth Weight

**Highest weight for the data plane.**

Recommended influence: **25%**.

##### Update 2026-08-26

Re-verified: nepa-mcp is in fast active development, not a static reference — five releases in the week before this pass (v0.1.3 on 2026-08-25), now at 20 servers / 47 tools / 32 GIS layers across 12 federal agencies. Stack: Python 3.12, standalone FastMCP 3.4.4, Pydantic 2, Shapely; `nepa-mcp doctor` and `list-servers` CLI. Two additions to "what to copy": its uniform five-file test taxonomy per server (unit/integration/security/resilience/performance, plus repo-wide catalog-honesty contract tests) — adopted in adapted form by design/testing-and-demos.md — and the fact that GSA's live catalog now carries its servers (§ 5 update), which makes federation with it an integration between active projects. Treat it as a moving neighbor: re-check before citing specifics.

### 4. Power-Agent

Repositories:
- https://github.com/Power-Agent/PowerMCP
- https://github.com/Power-Agent/PowerSkills
- https://github.com/Power-Agent/PowerAgentBench

#### 4.1 Observed Architecture

Power-Agent separates the ecosystem into distinct concerns.

##### PowerMCP
MCP servers expose power-system software and tools.

##### PowerIO
A canonical interchange representation lets models/cases move between otherwise incompatible simulation systems.

##### PowerSkills
Skills teach agents:
- what tools to use first,
- what to validate,
- when to escalate,
- what expert mitigation playbook to follow.

##### PowerAgentBench
Benchmark suite tests:
- evidence,
- safety,
- mitigation,
- efficiency,
- workflow,
- reliability.

#### 4.2 Architectural Philosophy

The important separation is:

```text
raw capability
     ↓
canonical interchange
     ↓
expert skill
     ↓
evaluation
```

This is one of the cleanest architectures observed.

#### 4.3 Strengths for Commonwealth

##### Extremely high
- Clear MCP vs skill separation.
- Progressive disclosure.
- Canonical interoperability layer.
- Independent benchmark suite.
- Contributor-friendly expert workflow layer.
- Domain knowledge can improve without rewriting MCP server code.

##### Commonwealth analogue

```text
PowerMCP            → Commonwealth MCP servers
PowerIO             → Commonwealth Core / CommonwealthIO
PowerSkills         → Commonwealth Skills
PowerAgentBench     → Commonwealth Bench
```

This is nearly a direct conceptual mapping.

#### 4.4 Weaknesses for Commonwealth

Power-system models have relatively stable entities:
- bus,
- branch,
- generator,
- load,
- transformer.

Government records are much less uniform.

A Commonwealth version of PowerIO must avoid building an overly broad universal government ontology.

The canonical layer should normalize only the entities needed for:
- identity,
- joins,
- provenance,
- geography,
- time,
- project/government action tracking.

#### 4.5 What to Copy

Copy:
- capability/skill separation,
- progressive disclosure,
- escalation triggers,
- canonical transport concept,
- benchmark discipline,
- CLI installation patterns.

Do not copy:
- assumption that all systems can map cleanly into one detailed canonical domain model.

#### 4.6 Commonwealth Weight

**Highest weight for overall layering.**

Recommended influence: **25%**.

### 5. GSA-TTS MCP Server Hub Catalog

**Repository:** https://github.com/GSA-TTS/mcp-server-hub-catalog

#### 5.1 Observed Architecture

This repository is not primarily an MCP implementation.

It is a **catalog/control-plane configuration repository** for a GSA-managed Obot MCP gateway.

One YAML entry per server declares:
- name,
- globally unique entry key,
- runtime type,
- remote endpoint or container image,
- health endpoint,
- shared vs per-user instance,
- credentials/environment configuration,
- display metadata,
- tool previews.

The gateway uses catalog entries to:
- populate catalog UI,
- connect to remote servers,
- deploy containerized servers,
- collect user credentials,
- isolate per-user instances.

#### 5.2 Key Distinction

GSA separates:

```text
MCP server implementation
```

from:

```text
MCP discovery/deployment/governance
```

That is the major lesson.

#### 5.3 `multiUser` vs `singleUser`

GSA's catalog distinguishes:

```text
multiUser
```

for public/keyless APIs with shared server instances, and:

```text
singleUser
```

for servers requiring personal credentials.

This maps well to Commonwealth.

##### Shared
- VGIN
- public ArcGIS
- Virginia Open Data
- Virginia Law
- public GTFS

##### Per-user
- API key-based systems
- authenticated restricted systems
- future transactional tools

#### 5.4 Strengths for Commonwealth

Very strong for:
- hosted multi-user operation,
- credential injection,
- container/runtime management,
- discoverability,
- health,
- versioning,
- control-plane metadata.

#### 5.5 Weaknesses for Commonwealth

It does not solve:
- source authority,
- field normalization,
- cross-source joins,
- government semantics,
- locality source resolution,
- project identity,
- workflow expertise.

A catalog entry can tell you how to run an MCP server.

It cannot tell you whether Fairfax County's zoning layer is authoritative relative to a statewide aggregation.

#### 5.6 What to Copy

Copy:
- separate control plane,
- declarative catalog,
- runtime metadata,
- health probes,
- tenancy,
- credential declarations,
- independently deployable servers.

Do not copy:
- its schema as the sole internal Commonwealth metadata model.

Recommendation:
Use a richer internal MCP catalog schema and support GSA/Obot format as an export target.

#### 5.7 Commonwealth Weight

**Highest weight for hosted control plane.**

Recommended influence: **18%** long-run.

For an MVP, lower priority than PNNL/Power-Agent.

##### Update 2026-08-26

The catalog is no longer hypothetical federal plumbing: 27 servers cataloged and served through GSA's Obot gateway, with the `multiUser` (keyless shared) vs `singleUser` (per-credential) split operating in practice — and about half the entries are PNNL's NEPA servers, i.e. a federal agency is running a gateway for exactly Commonwealth's category of geospatial/regulatory data servers. Entries follow the obot-platform/mcp-catalog YAML format with generated per-server doc pages. The "export target, not internal schema" recommendation stands; gateway selection criteria are design/0009.

### 6. GitHub MCP Server

**Repository:** https://github.com/github/github-mcp-server

#### 6.1 Observed Architecture

GitHub exposes one major remote MCP service with:
- local and hosted deployment options,
- OAuth or token authentication,
- domain-specific toolsets,
- read-only variants,
- different URL paths/toolset configurations,
- a default set and an "all" set.

Examples of toolsets include:
- actions,
- code security,
- discussions,
- Git,
- etc.

#### 6.2 Architectural Philosophy

A large capability surface should not automatically become one enormous active tool surface.

Instead:

```text
large backend capability set
       ↓
selective toolsets
       ↓
task-appropriate agent context
```

#### 6.3 Strengths for Commonwealth

Very useful for:
- one coherent user-facing gateway experience,
- task-specific tool activation,
- read-only profiles,
- reducing tool-selection confusion.

Commonwealth may eventually have >100 tools, but a land-development workflow should see perhaps 20–40.

#### 6.4 Weaknesses for Commonwealth

GitHub itself is one coherent platform:
- common auth,
- common API conventions,
- one vendor,
- one product domain.

Virginia government is inherently federated.

A literal one-process GitHub-style server risks excessive coupling.

#### 6.5 What to Copy

Copy:
- toolset exposure,
- default/all/read-only profiles,
- user-friendly remote endpoint model,
- hosted + local development options.

Do not copy:
- single-server physical topology as the long-term architecture.

#### 6.6 Commonwealth Weight

Recommended influence: **12%**.

##### Update 2026-08-26

GitHub's server now demonstrates the *consolidation* half of the story this section's weighting anticipated: a formal program collapsing endpoint tools into method-dispatch tools (`actions_get` with a `method` parameter absorbing five old tools), a 25-entry `DeprecatedToolAliases` map keeping renamed tools resolving for existing configs, and a documented rename process — still 91 tools across ~24 toolsets, so it is a direction, not an endpoint. The remote server adds per-toolset URLs (`/x/<toolset>` with `/readonly` variants) and an `X-MCP-Lockdown` header filtering low-trust content as a prompt-injection mitigation. Two additional patterns to copy: the alias mechanism (adopted by design/domain-servers.md § 1.6) and schema snapshotting ("toolsnaps", adopted by design/testing-and-demos.md).

### 8. Cloudflare Code Mode MCP

**Repository:** https://github.com/cloudflare/mcp

#### 8.1 Observed Architecture

Cloudflare also exposes a radically different model for the same broad API estate.

Rather than registering thousands of MCP tools, Code Mode exposes approximately:

```text
docs
search
execute
```

The server retains the large API specification and lets the agent search and execute against it server-side.

The repository argues that registering thousands of endpoint schemas consumes huge context while Code Mode keeps the tool surface tiny.

#### 8.2 Architectural Philosophy

```text
huge API surface
    ↓
few generic meta-tools
    ↓
server-side schema search
    ↓
dynamic execution
```

#### 8.3 Strengths for Commonwealth

Very high for:
- long-tail source coverage,
- large ArcGIS/OpenAPI estates,
- contributor exploration,
- sources not yet normalized,

- authority rules,
- stable source selection,

- provenance,


with:

- read-only enforcement,
- sandboxing,

#### 8.6 Commonwealth Weight

Cloudflare overall: **10%**.

As primary architecture: medium.

As long-tail fallback: very high.

### 17. What Commonwealth Should Avoid

#### 17.1 Avoid One Server Per County

If 133 Virginia localities imply 133 MCP servers, the platform abstraction has failed.

#### 17.2 Avoid One Tool Per API Endpoint

This leads to:
- context explosion,
- poor tool selection,
- vendor schema leakage.

#### 17.3 Avoid Pure Semantic Retrieval

Government research often requires exhaustive deterministic queries, not just relevant snippets.

#### 17.4 Avoid Browser-First Integration

Use official APIs and bulk data wherever possible.

#### 17.5 Avoid Skill Logic Inside Tools

A zoning lookup tool should not decide whether a project is entitled.

#### 17.6 Avoid Authority Logic Inside Adapters

ArcGIS adapter should not know whether locality zoning is legally controlling.

That belongs in source metadata and skills.

#### 17.7 Avoid Unreviewed Fuzzy Entity Merging

Keep ambiguous project/company matches visible.

#### 17.8 Avoid Treating "Public" as "Automation Allowed"

Source terms must be explicit.

### 1. Headline shifts since the reference evaluation

1. **The flagship server is consolidating tools, with a migration mechanism.** github-mcp-server (32.5K★, releasing weekly) now runs a formal consolidation program: many endpoint tools collapse into method-dispatch tools (`actions_get` with a `method` param absorbing five old tools), a `DeprecatedToolAliases` map (25 aliases) keeps old names resolving, and `docs/tool-renaming.md` documents the process. Still 91 tools across ~24 toolsets, so consolidation is a direction, not a finished state. The remote server adds per-toolset URLs (`/x/<toolset>`, each with `/readonly`) and an `X-MCP-Lockdown` header that filters low-trust content (issues from non-push users) as a prompt-injection mitigation: content trust as a server feature.
2. **Cloudflare's two strategies are permanent, not sequential.** The Code Mode server covers ~2,500 endpoints with 3 tools (~1,100 tokens vs ~1.17M for full schemas — their own table), executes model-written JS in isolated Workers, and offers `?codemode=false` to revert to per-endpoint tools; the ~16 domain servers continue separately, migrated to stateless SDK v2 with legacy SSE endpoints returning 410 Gone. The vendor's own framing: broad-access code mode and curated typed tools are purpose-fit siblings.
3. **AWS moved its production story off awslabs/mcp.** The repo (57 servers, still active) now banners "Agent Toolkit for AWS" (launched ~May 2026) as its successor: IAM condition keys distinguishing agent from human actions, CloudTrail/CloudWatch visibility, evaluated skills. Cite awslabs/mcp as a large working collection in coast mode, not as AWS's current thinking.
4. **The reference-server repo shrank on purpose.** modelcontextprotocol/servers is down to 7 pedagogical servers; 13 (GitHub, Slack, Postgres, Puppeteer...) moved to `servers-archived` with successors named; the README now routes discovery to the official registry. "Many first-party servers in one repo" is no longer the stewards' own shape.
5. **PNNL's nepa-mcp is in active, fast development.** Five releases in the week before this survey (v0.1.3 on 2026-08-25); now 20 servers, 47 tools, 32 GIS layers over 12 federal agencies; Python 3.12 + standalone FastMCP 3.4.4 + Pydantic + Shapely; `nepa-mcp doctor`; a `map_composer` cross-source server. Its test discipline is the strongest close-domain pattern found (§ 7).
6. **GSA's hub catalog is live government adoption of the gateway pattern.** 27 servers cataloged (about half of them PNNL's NEPA servers) feeding a GSA-managed Obot gateway, with the `multiUser` (keyless shared) vs `singleUser` (per-credential) split in production use. A federal agency is operating a gateway for exactly Commonwealth's category of geospatial/regulatory servers.

### 2. New exemplars and what each one teaches

**getsentry/sentry-mcp** — the production remote-server template. Explicitly a curated middleware ("not a general-purpose API wrapper"); tools grouped into named *skills* (`inspect`, `triage`, `seer`) selectable per-request (`?skills=`); MCP OAuth plus a pass-through upstream-token mode on a deliberately non-`Bearer` header; monorepo with mocks, evals, and a custom test CLI as first-class packages. Its three-tier test strategy is § 7's pattern 2.

**Esri (MCP for ArcGIS Location Services)** — closed hosted beta, capability-grain tools (geocoding, routing, elevation, places, GeoEnrichment), API-key or OAuth. No open-source template to copy, and the community ArcGIS-MCP field is fragmented small projects. Consequence: Commonwealth's ArcGIS adapter and geo tool conventions will be defined, not borrowed, and Esri's capability-grain naming supports the semantic-tool bet.

**Open-data-portal servers (Socrata/CKAN)** — no official vendor server on either platform (a search-surfaced `socrata/odp-mcp` does not exist; verified 404). The norm is many narrow namespaced tools (ondata/ckan-mcp-server: 21 tools, 57★; city-scoped Zurich/Berlin servers exist). Standout: **npstorey/civic-ai-tools** (41★, active) targets all 559 Socrata portals with an explicit anti-hallucination layer — "record packages" aiming at inspectable, reproducible, cryptographically verifiable analyses, ADRs, trust-and-evidence docs, and runnable `examples/` scripts against live data. Closest philosophical neighbor to Commonwealth's provenance envelope found anywhere.

**Federal/civic servers** — two genuinely official federal servers verified: **uscensusbureau/us-census-bureau-data-api-mcp** (92★, official Census Bureau, tools like `fetch-aggregate-data`/`resolve-geography-fips`; quiet since 2026-03; local Docker/Postgres setup, no verified hosted endpoint) and **GPO's GovInfo MCP** — a public-preview hosted endpoint at `https://api.govinfo.gov/mcp` (api.data.gov key; two tools, `searchGovInfo` + `describePackageOrGranule`), documented at `usgpo/api` (`docs/mcp.md`), which resolves this survey's earlier "repo location unverified" gap (found in the 2026-08-26 second research round: RESEARCH.md part 5 § 3). Also official: Data Commons' hosted MCP (compact six-tool statistical surface, ibid. § 2). CMS and Treasury list MCP in AI inventories. Everything else is community: congressMCP (32★, keyless-first, 19-client compatibility docs) is the most developed; SLED-scoped `cliwant/mcp-sam-gov` claims 150 tools across federal and state/local contracting; a recognizable one-author-many-servers family (cyanheads) covers census/usaspending/socrata. Three independent projects converge on "keyless-first, verifiable citations, honesty-hardened" framing — the niche's felt need, and Commonwealth's design center, arrived at independently.

**stripe/agent-toolkit ("Stripe AI")** — one capability layer shipped three ways: Python/TS SDKs, a hosted OAuth MCP server, and harness-native skill plugins (Claude/Codex/Cursor marketplaces). Plus the most rigorous eval convention surveyed: per-task `environment/` (agent-visible), `grader/` (hidden), `solutions/` (hidden), best-of-3 scoring, human-reviewed winning transcripts, dated results CSV.

**jlowin/fastmcp (PrefectHQ stewardship)** — 27K★, 3.4.7 stable / 4.0 beta; claims a dominant ecosystem share (self-reported). Ships auth providers, middleware, composition, tool transformation, versioned docs, and two ideas of independent interest: documented in-memory-transport pytest pattern (§ 7 pattern 5) and `tool-fingerprinting` (schema hashing against drift/rug-pull tampering). Its commercial gateway (Prefect Horizon) signals where its maintainers see governance heading. Note for DECISIONS.md 0003: PNNL — the closest domain analog — builds on standalone FastMCP 3.4.4, which is real evidence against the official-SDK-only reading.

**grafana/mcp-grafana** — the "many narrow tools at scale" template done carefully: 97 tools in ~28 product-mirroring categories; the tool table declares required RBAC permissions and scopes per tool; read-only mode enumerates every disabled tool by name; the server instruments itself (metrics, tracing, slow-request logs).

**Notion (hosted redesign)** — the primary-source consolidation case study: 1:1 API tools produced token-heavy hierarchical JSON and poor agent experiences; the hosted server rebuilt around few agent-oriented tools (`create-pages`, `search`) plus "Notion-flavored Markdown" as a dense content representation. The transferable lesson: consolidation succeeds by redesigning the *response format*, not by merging signatures. (The open-source local repo remains endpoint-shaped, 22 tools, and is being deprioritized by Notion.)

**NERVsystems/osmmcp** — a third tool-design philosophy, deliberately reasoned: composable primitives (uniform parameter names, single responsibility, output-as-input compatibility, no side effects, precise errors) *plus* curated composite tools, both exposed simultaneously; 25 tools in one registry file; TTL caching in front of rate-limited public APIs; Prometheus + OTel in a 28★ project.

### 3. The tool-design taxonomy the survey supports

Three coexisting philosophies, each with a flagship and a fit:

| Philosophy | Flagships | Fits when |
|---|---|---|
| Few consolidated workflow tools | Notion hosted, github-mcp-server's direction, Anthropic guidance | High-level user intents; hierarchical data that needs a dense format |
| Many narrow tools, grouped + governed | grafana, CKAN servers, Supabase feature groups | Surface mirrors a real product/API taxonomy; per-tool authz matters |
| Composable primitives + curated composites | osmmcp; Cloudflare code mode as the extreme | Spatial/analytical domains where chains are unforeseeable |

Commonwealth's semantic-tool design is philosophy 1 at the user surface with philosophy 3 underneath (geo primitives like `intersect`/`buffer` alongside `find_zoning` composites) — osmmcp demonstrates the combination working, and its five primitive-design principles read as a checklist for `geo.*`. Supabase adds the governance twist worth copying: feature groups toggle *registration*, scoping disables whole groups, and read-only is enforced at the data layer (their Postgres read-only role), not just the tool list — defense in depth Commonwealth can mirror by having adapters expose only read verbs at the client-construction level.

### 4. Gateways and registries, one screen

- **Docker mcp-registry/Toolkit**: curated, container-isolated, supply-chain-first (signatures, SBOMs for Docker-built images); consumer/desktop distribution.
- **IBM ContextForge**: 4.4K★ federation gateway (MCP+A2A+REST), OTel-first, Kubernetes-scale; enterprise shape.
- **Obot**: governance/identity-first, composes virtual servers from selected tools across servers, request/response filters; the one a federal agency (GSA) actually runs.
- Discovery-only: Smithery, Glama (tracking ~37K servers mid-2026, secondhand), PulseMCP (hand-reviewed), mcp.so, awesome-mcp-servers; common advice is to list in several.
Consequences live in DECISIONS.md 0009 (criteria over a pick) and design/hub-catalog.md; the official registry's aggregator model (RESEARCH.md part 1 § 3) is the piece that makes "publish once, appear everywhere" plausible.

### 5. Civic gap, stated plainly

Nothing occupies the state/county/municipal layer: no state government publishes to the MCP registry; the strongest civic projects are federal-scoped or single-city; the ArcGIS/Socrata/CKAN wrapper field has no dominant template; and the independent projects nearest in spirit (civic-ai-tools, congressMCP) converge on Commonwealth's exact design values from different starting points. The gap is real and the timing is early enough that conventions Commonwealth sets (manifest schema, provenance envelope, jurisdiction IDs) could become the ones others copy.

### 6. What the survey changes in Commonwealth's plans

1. **Adopt the alias discipline before it's needed.** Tool renames are inevitable; github-mcp-server's deprecation-alias map + toolsnaps is the compatibility mechanism, cheap to build from day one (design/testing-and-demos.md).
2. **Ship read-only as enumeration + construction, not adjective.** Grafana's named-tools read-only list and Supabase's data-layer enforcement combine into: every Commonwealth server documents its (empty in V1) write-tool list, and adapters are constructed read-only.
3. **Borrow the lockdown idea for content trust.** `X-MCP-Lockdown` is a server-side mitigation for untrusted content inside trusted sources; Commonwealth's analog is the injection-trap bench tasks plus the manifest's `data_classification`/content-trust fields; a filtering mode is a plausible later feature.
4. **The skills-as-tool-groups pattern (Sentry) and per-request group selection** reinforce toolset design (DECISIONS.md 0002); the `?skills=` query-param mechanism is worth copying for remote deployments.
5. **Watch nepa-mcp as a moving neighbor, not a snapshot.** It ships weekly, uses standalone FastMCP, and GSA already catalogs it; federation with it (design spec § 17's environmental screen) is integration with an active project, and its conventions (doctor CLI, 5-file test taxonomy) are current, not historical.

### 7. Test/demo patterns worth copying (ranked)

Full detail in research/notes/ecosystem-notes.md; the eight patterns with sources:

1. **Uniform per-server test taxonomy** (pnnl/nepa-mcp): every server gets the same five files — unit, integration, security, resilience, performance — plus repo-wide contract tests keeping the generated tool catalog honest against registrations.
2. **Three-tier testing with LLM-graded evals** (sentry-mcp): unit (mocked upstream via MSW) → `vitest-evals` driving a real model through the tools in CI → documented manual CLI testing. The eval tier catches "schema is right but a model can't use it."
3. **Hidden-grader agentic benchmarks** (stripe/agent-toolkit): `environment/` visible, `grader/` and `solutions/` hidden, best-of-3, human-reviewed transcripts, dated leaderboard CSV.
4. **Known-failures baseline + reconciliation audits** (congressMCP): `KNOWN_FAILURES.md` asserted by tests so new upstream breakage stands out from cataloged quirks; dated upstream-reconciliation audit docs; a tool-defect register. Built for flaky government upstreams — Commonwealth's exact weather.
5. **In-memory transport + snapshot assertions** (fastmcp): `Client(transport=server)` in a pytest fixture, `inline-snapshot` for structures, `dirty-equals` for fuzz — the tight dev loop without Inspector or subprocesses.
6. **Toolsnaps + deprecation aliases** (github-mcp-server): snapshot the tool *schemas*, link schema/tests/snaps updates in one change, alias renamed tools.
7. **Runnable live-data examples** (civic-ai-tools): `examples/*.py` via `uv run`, graceful keyless degradation, Codespaces one-click.
8. **MCP Inspector as the universal baseline** — every serious repo points to it beneath their own automation.

Adoption priority for Commonwealth: 4 (the domain fit is exact), 1 (trivially applicable to multi-server layout), then 3 (when bench matures beyond fixtures). Patterns 5 and 6 fold into ordinary test scaffolding; 7 is the demo story; design/testing-and-demos.md turns this ranking into structure.

### 1. The tool-count ceiling is real, measured, and lower than people expect

The most consistent complaint across every channel: agents degrade when too many tools sit in context, and MCP makes it easy to oversubscribe.

- A production audit found Claude Haiku 4.5 drops below 90% tool-selection accuracy between 10 and 15 tools in context; Sonnet-class models hold to somewhere between 20 and 30 ([Medium, "91% at 10 Tools, 87% at 15"](https://medium.com/@meshuggah22/91-at-10-tools-87-at-15-the-five-architecture-patterns-behind-reliable-mcp-servers-11fef1bbe401)).
- The mcp2cli launch measured 96-99% token overhead for tool schemas against equivalent CLI invocations ([HN 47305149](https://news.ycombinator.com/item?id=47305149)). An Arize eval found a repo-language question cost a CLI agent 1,365 tokens and an MCP agent 44,026, almost all of it 43 injected tool definitions ([Arize](https://arize.com/blog/mcp-vs-cli-skills-for-agents-what-our-eval-found-and-which-you-should-use/)).
- Claude Code now truncates any tool result over 25K tokens, which callers described as still too permissive: "three or four Playwright snapshots and you've burned 100k tokens on raw data you only needed a few lines from" ([HN 47193064](https://news.ycombinator.com/item?id=47193064)).

**Implication for Commonwealth.** The design spec's 20-50 active tool budget is defensible but sits above the measured comfort zone for smaller models. Toolsets should default nearer 15-25, and the benchmark suite should measure tool-selection accuracy per toolset size on at least two model tiers. Result envelopes need a token budget of their own (summary + resource handle, section 7).

### 2. "Thin wrapper per endpoint" is the named anti-pattern of the ecosystem

Multiple independent sources converge on the same failure: generating one MCP tool per REST endpoint and hoping the model sequences them.

- AWS's tool-design guidance and several 2026 postmortems treat endpoint-mirroring as the first mistake to avoid, recommending outcome-shaped tools that do the orchestration server-side ([AWS ML blog](https://aws.amazon.com/blogs/machine-learning/mcp-tool-design-practical-approaches-and-tradeoffs/), [digitalapplied anti-patterns guide](https://www.digitalapplied.com/blog/mcp-server-anti-patterns-design-mistakes-2026-developer-guide)).
- A widely-shared HN comment from a developer on their fourth MCP server: they stopped hand-curating dozens of tools and shipped a single query tool "but with tons of documentation about the table... So less coding, more prose" ([HN 43600192 replies](https://news.ycombinator.com/item?id=43600192)). Description quality did the work the tool count was failing to do.
- Reviewers called the official GitHub server "a bloated mess of tools" when it was used as a benchmark baseline ([HN 45347914](https://news.ycombinator.com/item?id=45347914)); GitHub's own answer was toolsets and read-only profiles.
- The counterexample that got praise: Notion collapsed many API endpoints into a small set of workflow tools designed around what users ask for, and vendors that did the same reported better completion rates.

**Implication for Commonwealth.** The spec's "semantic tools, boring adapters" rule matches the field consensus exactly. The addition worth making: invest in tool *descriptions* as first-class engineering artifacts (with review, versioning, and eval coverage), because several practitioners found description quality moved results more than tool-surface shape.

### 3. The CLI/Skills challenge: know why MCP survives it, and design for that reason

Through late 2025 and 2026 a loud contingent argued MCP is overhead: agents that can run code do better with CLIs and skill files. Anthropic's own Playwright-Skill comparison and code-execution post fed this ([HN 45642911](https://news.ycombinator.com/item?id=45642911), [Anthropic engineering](https://www.anthropic.com/engineering/code-execution-with-mcp)). An 800-token skill file outperforming 28K tokens of schema is the meme version ([themenonlab](https://themenonlab.blog/blog/skills-vs-mcp-token-efficiency-ai-agents)).

The rebuttals that survived contact, mostly from the Zero-Touch OAuth thread ([HN 48592163](https://news.ycombinator.com/item?id=48592163)):

1. **Auth isolation.** MCP keeps credentials out of the model's context and out of the harness. "Maybe the idealized form of MCP is just an auth gateway for the API" (sean_lynch). Skills and CLIs put secrets in reach of generated code.
2. **The semantic layer travels with the server.** "Skills are client side and don't know the server's capabilities. MCP lets the server explain its API... so clients who have no prior knowledge of the server can use it intelligently" (brookst, a self-described convert after building two large servers).
3. **Audit and centralized control.** Per-tool audit trails, org-level rollout, and revocation have no skills equivalent; the state of the art for deploying skills is "copy this file into this place" (mooreds).
4. **No local runtime required.** Hosted agents in restricted containers can't run arbitrary CLIs; remote MCP is how non-developer users connect anything at all (9dev, lavataco).
5. **Non-binary.** "Which is better, a knife or a saw?" (Ferret7446). Teams increasingly ship MCP for connection/auth/data and skills for workflow knowledge on top.

**Implication for Commonwealth.** Commonwealth's audience includes exactly the users the CLI camp ignores: researchers and civic developers who will connect claude.ai or a desktop client to a hosted endpoint and never run a terminal. MCP-first is right. But the token criticism is also right, so the architecture should treat context cost as a budget (small default toolsets, summarized results, skills for workflow knowledge) and ship a CLI for developers so nobody is forced through MCP for scriptable work. The design spec already leans this way; the research confirms it and hardens the numbers.

### 4. Security: the community assumes MCP servers are hostile until proven otherwise

The security threads are the largest and angriest of the corpus ([HN 43600192](https://news.ycombinator.com/item?id=43600192), [44219755](https://news.ycombinator.com/item?id=44219755), [45348183](https://news.ycombinator.com/item?id=45348183), [44617910](https://news.ycombinator.com/item?id=44617910)). The catalog that recurs:

- **Tool poisoning.** A malicious tool description instructs the model to misuse *other* tools ("you're also allowing the random company to trick the AI into telling them your SSH key").
- **Parameter poisoning.** Simon Willison's example of an `add(a, b, content_from_reading_ssh_id_rsa)` signature that naive clients render as harmless.
- **Output poisoning (ATPA).** Even a tool's error messages can carry injected instructions; "every piece of text could be turned into malicious code at any moment."
- **The lethal trifecta.** Private-data access + untrusted content + an exfiltration channel guarantees exploitability regardless of model quality ([simonwillison.net](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). OWASP's June 2026 agentic-security report mapped prompt injection into six of its top ten agentic categories ([Help Net Security](https://www.helpnetsecurity.com/2026/06/11/owasp-prompt-injection-ai-security-failures/)).
- **Supply chain.** "Third party MCP servers at this point are basically just attack vectors. How do you even vet them continuously?" Enterprise workarounds are allowlists of major-vendor servers only.
- **Observability gap.** "Also the O is for Observability... most implementations do not have any auditing or metrics."
- Auth-flow implementation bugs produced real RCEs in major clients (the "From MCP to shell" disclosures), so protocol-level auth care is not theoretical.

**Implication for Commonwealth.** A public-data, read-only server suite is on the safe end of this spectrum, and should say so precisely rather than loudly. Concretely: government-published data is still *untrusted content* for injection purposes (a council agenda PDF can carry adversarial text), so results should be treated as data, never instructions; no tool should take a free-form URL or emit arbitrary outbound requests (registry-allowlisted endpoints only, which the spec's escape-hatch rule already requires); audit logging is table stakes, not an enterprise add-on; and the trust story (what Commonwealth servers can and cannot touch) belongs on page one of the docs, because vetting anxiety is now the default posture of any security-conscious adopter.

### 5. Auth friction is the #1 adoption complaint for remote servers; the fix is arriving

Practitioners describe OAuth for MCP as "a wild journey." Dynamic client registration confused everyone; enterprises hated per-user consent for org data. The response, shipped mid-2026: Enterprise-Managed Authorization (EMA), a stable MCP extension built on the IETF ID-JAG draft (cross-app access), letting an identity provider authorize agent-to-server connections centrally ([HN 48592163](https://news.ycombinator.com/item?id=48592163)). Anthropic, Okta, Microsoft, Figma, and Linear shipped support.

**Implication for Commonwealth.** V1's public read-only posture means anonymous access, which sidesteps the pain entirely and is worth preserving as long as possible ("no login" is a feature civic developers will notice). When authenticated tiers arrive (Phase 5), EMA/ID-JAG is the pattern to target for institutional users (a university authorizing its researchers) rather than per-user OAuth consent screens.

### 6. Discovery is drowning: registries are supply-driven, and trust is the scarce good

- The official registry passed 20,000 listed servers by August 2026 (`tools/fetch_mcp_registry.py` snapshot; the count is a floor, since the crawl paged out at 20K). The listing shows heavy duplication and commercial noise; civic-keyword matches are dominated by real-estate and marketing servers, with almost no government publishers.
- swyx, on the failed mcpt registry: "there's significant SUPPLY for what he built... everyone is just trying to self promote by putting mcp wrappers of their stuff out. the hard part is the demand" ([HN 44016336](https://news.ycombinator.com/item?id=44016336)).
- "There's a huge gap in this market for someone who can take these and make them trustworthy" (same thread); Docker's curated catalog is the cited attempt.

**Implication for Commonwealth.** Being listed is worthless; being *the* trusted, authoritative source for Virginia government data is the entire value proposition. Publish to the official registry with verified namespaces, but treat the project's own catalog, provenance discipline, and institutional signals (data.virginia.gov linkage, agency acknowledgment where possible) as the real discovery surface. A Commonwealth server should be findable by what it answers, and its authority should be checkable.

### 7. Result design: summarize, index, let the agent come back for detail

The highest-starred context-management projects converge on one shape: return a compact summary now, keep the full payload retrievable later. context-mode (FTS5 index over full outputs, "give me the summary now, let me come back for specifics later"), Strata (progressive navigation: server → category → action → detail, "a search engine vs. a file explorer", which its founders also pitch as a dynamic allowlist shrinking blast radius), and Anthropic's code-execution post all implement the same idea at different layers ([HN 47193064](https://news.ycombinator.com/item?id=47193064), [45347914](https://news.ycombinator.com/item?id=45347914)).

**Implication for Commonwealth.** The spec's resource-handle pattern (`commonwealth://results/{id}`) is the right mechanism and predates this wave; the research adds sizing discipline: set a per-result token budget (a few KB), return record counts plus a handful of exemplar rows, and make the full result set addressable by resource URI and queryable (filter/page against a cached result) rather than only downloadable.

### 8. Agents second-guess literal inputs; deterministic lookups must pin them down

From the Mapbox geospatial MCP thread: given a fuzzy place-search tool, the model substituted its world-knowledge guess ("cal academy" → California Academy of Sciences) instead of passing the user's literal string through, and a commenter noted it would happily do so even when wrong ([HN 44247124](https://news.ycombinator.com/item?id=44247124)). Testing showed agents consult their priors alongside tools, sometimes checking multiple candidate interpretations.

**Implication for Commonwealth.** This is the jurisdiction-resolution problem in miniature (Fairfax City vs. Fairfax County). Tools should accept the raw user string, return ranked candidate resolutions with the evidence for each, and never let the model's silent guess stand in for a resolution step. The bench suite should include disambiguation traps, which the spec's eval task list already sketches.

### 9. Determinism, testing, and evals are the ecosystem's weak spot

- "It amazes me that they're so good at coding when they're so bad at tool use" ([HN 45347914](https://news.ycombinator.com/item?id=45347914)); teams that measured tool-use quality (Strata, Notion) treated eval numbers as the product claim.
- The skills-vs-MCP determinism argument ("MCPs are deterministic, SKILLS.md isn't") was picked apart in-thread: the tool may be deterministic, the system isn't, so only end-to-end evals say anything.
- Very few servers ship benchmarks at all; reviewers asking "is there a benchmark?" of new tools became a refrain.

**Implication for Commonwealth.** Shipping Commonwealth Bench alongside V1 is a differentiator, and the public/hidden split the spec borrows from PowerAgentBench matches what the strongest teams do privately. Publishing per-toolset accuracy numbers would be nearly unique among civic data projects.

### 10. Docs and README practices: generated prose now costs credibility

Two threads in the corpus turned on writing quality rather than code:

- On mcp2cli: "This post and the project README are obviously generated slop, which personally makes me completely skip the project altogether, even if it works. If you want humans to spend time reading your prose, then spend time actually writing it" ([HN 47305149](https://news.ycombinator.com/item?id=47305149)). A second commenter quoted the tell ("We measured this. Not estimates — actual token counts...").
- The Octelium launch drew sustained criticism for a buzzword README that hid a real system; the fix praised in-thread was the doc page that "starts by explaining the core primitives... and builds up from there" ([HN 44412207](https://news.ycombinator.com/item?id=44412207)).

**Implication for Commonwealth.** House anti-slop rules (base-files/DESIGN.md § 11.1, enforced by `tools/check_writing.py`) apply to the READMEs, tool descriptions, and error messages, which are themselves agent-facing surfaces. Structure docs primitives-first: source registry → adapters → tools → skills, one concept per page, before any feature list.

### 11. Scattered practical advice worth keeping

- Error messages are for the model: name the failure class, say what to try next ("distinguish no-results from no-coverage" has direct HN precedent in complaints about tools returning empty arrays for outages).
- Verbose, example-rich tool descriptions measurably improve use; treat them like prompts, with the same review discipline ([HN 46207425 replies](https://news.ycombinator.com/item?id=46207425)).
- Sandboxing and packaging: OCI-packaged, signed plugins with no default network/filesystem access got repeated approving mention (hyper-mcp); relevant if Commonwealth ever runs community-contributed adapters.
- Composability keeps coming up: developers wrap MCP servers in CLIs and CLIs in MCP servers; publishing a clean CLI (`commonwealth ...`) alongside the servers serves both camps, and the spec already commits to one.
- Foundation governance landed well: MCP moved to the Agentic AI Foundation under the Linux Foundation in late 2025 with A2A already there; "MCP works everywhere" is now the default assumption, and skills are widely read as complementary, with adoption arguments settled enough that betting an ecosystem project on the protocol no longer reads as risky ([HN 46207425](https://news.ycombinator.com/item?id=46207425)).

### What did NOT show up

Three absences worth recording, because they are opportunities:

1. **No state-level government MCP suite exists.** Federal precedent is real (Census Bureau and GPO ship official servers; CMS and Treasury list MCP in AI inventories; France and India have national equivalents) ([Paubox](https://www.paubox.com/blog/feds-adopt-open-source-protocol-to-connect-ai-chatbots-with-public-data)), and community civic servers exist for federal APIs, but nobody has shipped the state/county/municipal layer Commonwealth targets.
2. **Provenance envelopes are almost unshipped.** No mainstream server returns publisher/authority/coverage metadata with results. The nearest prior art surfaced later in the repo survey: npstorey/civic-ai-tools' "verifiable record package" framework and a small cluster of civic servers self-describing as "verifiable citations, keyless-first" (RESEARCH.md part 3 § 2, § 5) — same instinct, no shared contract. Commonwealth's envelope would still be the first systematic version, with those projects as allies rather than templates.
3. **Almost nobody publishes evals.** Section 9; the gap is the opening.

### 2. Data Commons MCP

Primary source: https://docs.datacommons.org/mcp/

Data Commons now operates an official hosted MCP and offers a Python package and container for self-hosting. Its tool surface is compact:

- `search_indicators`
- `search_child_indicators`
- `get_variable_metadata`
- `get_observations`
- `get_child_observations`
- `get_multi_entity_observations`

It also publishes workflow skills as MCP resources. That is useful evidence for Commonwealth's eventual skill-distribution direction.

Relevant lessons:

1. Discovery is separate from retrieval. The agent searches indicators, checks metadata and coverage, then fetches observations.
2. Place hierarchy is part of the tool contract.
3. Source metadata and available dates are explicit retrieval steps.
4. A small tool surface can cover a large statistical graph.
5. Skills can teach agents the correct multi-step path without adding more tools.

Recommended use:

- Optional demographics, health, economic, housing, education, and population context.
- Mark as aggregated or derived authority. Data Commons combines many upstream publishers and cannot replace a locality's primary record.
- Preserve Data Commons' own source-facet metadata inside Commonwealth evidence.
- Do not route events, local proceedings, legal status, or non-geographic entities through it; the official service lists those as unsupported.

Integration choice: external federation first. A Commonwealth wrapper is justified only when a workflow requires uniform evidence references or coverage fields.

### 3. GovInfo MCP

Primary source: https://github.com/usgpo/api/blob/main/docs/mcp.md

The U.S. Government Publishing Office runs a public-preview endpoint at `https://api.govinfo.gov/mcp`. It requires an api.data.gov key and exposes two tools:

- `searchGovInfo`
- `describePackageOrGranule`

The first returns publication metadata, dates, identifiers, links, and teasers. The second retrieves package or granule details, rendition links, metadata links, and optional excerpts.

Relevant lessons:

1. Two tools can cover a large publication corpus when discovery and retrieval are cleanly separated.
2. Stable official identifiers should flow from search into retrieval.
3. Rendition links are better than pushing full PDFs, XML, or ZIP files through model context.
4. Publication date and system-update date are different and both matter.

Recommended use:

- Federal statutory and regulatory publication context.
- Official federal documents referenced by Virginia actions.
- Bill-to-enacted-publication verification where the workflow needs federal material.

Integration choice: catalog the official endpoint. Add a wrapper only when evidence-envelope normalization is necessary. Treat public-preview status as an operational risk and run compatibility checks before each release.

This resolves the prior research gap about the GPO repository location.

### 4. U.S. Census Bureau Data API MCP

Primary source: https://github.com/uscensusbureau/us-census-bureau-data-api-mcp

The official Census Bureau project exposes four tools:

- `list-datasets`
- `fetch-dataset-geography`
- `fetch-aggregate-data`
- `resolve-geography-fips`

It supplements live Census API calls with a local Postgres database for richer dataset and geography search. Current setup requires Docker, Node, an API key, migrations, and seeded data.

Relevant lessons:

1. Metadata search may need a local index even when the authoritative values remain live API calls.
2. Geography resolution deserves its own tool.
3. Dataset, vintage, variable, group, and geography are independent query dimensions.
4. Tool schemas live separately and are tested as contracts.

Recommended use:

- FIPS validation and demographic/economic statistics.
- Benchmark Commonwealth jurisdiction IDs against Census geography identifiers.
- Compare official Census MCP output with direct Census API adapter output.

Integration choice: list as an official external server, but do not make V1 depend on its Docker/Postgres installation. Commonwealth's Census geocoder and basic aggregate lookups can call official Census APIs directly through registered adapters. Revisit remote federation if an official hosted endpoint appears.

### 5. BetaNYC Council MCP and the Legistar pattern

Primary source: https://github.com/BetaNYC/nyc-council-mcp

BetaNYC uses a two-speed architecture:

```text
local SQLite index
  -> sub-second search, history, aggregation, voting analysis

live Legistar API
  -> current status, upcoming hearings, confirmation
```

Its tool set includes local search and aggregation plus live confirmation tools such as `get_bill`, `get_upcoming_hearings`, `get_votes`, and `search_legislation_live`. It also rejects ambiguous bare bill identifiers instead of guessing between matter types.

Relevant lessons:

1. Search and authoritative confirmation can use different storage paths.
2. Freshness mode must be visible in every result.
3. Local indexes need schema-version and source-set rebuild triggers.
4. Human-openable links may not be derivable from API IDs. Wrong links are worse than null links.
5. Ambiguous identifiers should return candidates.

Recommended use:

- Build the future `legistar` adapter around `search -> confirm` rather than pretending one query path serves every need.
- Keep local-index results labeled with index vintage.
- Require live confirmation for current status and upcoming meetings.
- Preserve locality-specific matter types instead of forcing them prematurely into one enum.

Integration choice: architecture reference, not Virginia federation. Before reusing code, inspect its license and isolate generic Legistar logic from NYC-specific archive assumptions.

### 6. OpenStates MCP

Primary source: https://github.com/cyanheads/openstates-mcp-server/blob/main/README.md

This community server exposes ten tools over the Open States API: bill, legislator, committee, event, and jurisdiction search/retrieval, plus coordinate-to-legislator resolution.

Relevant lessons:

1. Coordinate-to-representative is a useful composite over jurisdiction and district boundaries.
2. Open Civic Data identifiers can bridge state-level datasets.
3. Coverage varies by state and by object class; committee and event coverage is explicitly experimental.

Recommended use:

- Optional cross-state discovery and gap-filling.
- Cross-checking representative and district resolution.
- Future portability testing after Gate G.

Integration choice: optional external catalog entry. Classify as third-party or official-derived, not primary. Virginia LIS and locality systems remain authoritative for Virginia legislative status and proceedings.

### 7. GTFS MCP

Primary source: https://github.com/jdamcd/gtfs-mcp

The project configures one or more transit systems through data rather than code. Eleven tools cover systems, stops, routes, arrivals, vehicles, alerts, trips, and feed health. Static schedules are downloaded and cached; GTFS-Realtime feeds are queried for current state. IDs returned by one tool are accepted by the next.

Relevant lessons:

1. One manifest can describe static and several realtime feeds.
2. Agency timezone is required for correct "now" behavior.
3. Feed health is a first-class capability, not an operator-only endpoint.
4. Output-as-input ID compatibility makes primitives composable.
5. Model-selection evals and real-feed invariant campaigns complement fixture tests.

Recommended use:

- Reference for the Phase-2 `gtfs` adapter.
- Add manifest fields for timezone, schedule cadence, realtime feed types, credentials, and feed health.
- Keep alerts and vehicle positions on short TTLs while schedules use longer cache windows.
- Treat first-download size and cold-start behavior as acceptance criteria.

Integration choice: learn from it first. Evaluate license, protocol revision, security posture, and Virginia-feed behavior before forking or cataloging it.

### 8. Imaging Data Commons: one core, multiple surfaces

Primary source: https://github.com/ImagingDataCommons/IDC-REST-MCP

This public-data project uses one backend-agnostic core with thin REST and MCP adapters. It also documents when developers should use REST, MCP, or a code-execution skill. Capabilities are implemented and tested once.

Relevant lessons for Commonwealth:

1. MCP is a caller surface, not the business-logic boundary.
2. REST serves scripts, apps, notebooks, and websites; MCP serves agent callers.
3. Large downloads should transfer directly from source storage rather than through the MCP server.
4. A read-only local analytical database can be baked into a stateless image.
5. License and citation output can be a product capability.
6. Read-only query escape hatches need their own threat model.

Recommended architecture change:

```text
commonwealth core capabilities
  -> Python library
  -> CLI
  -> MCP adapter
  -> REST/OpenAPI adapter in the hosted phase
```

This better matches the project's stated audience. Indie and university developers should not need an MCP client to consume Commonwealth capabilities.

### 9. Tool patterns to adopt

Across these projects, the strongest repeated shapes are:

#### Discovery then retrieval

Examples: Data Commons, GovInfo, Census.

Use when the identifier or dataset is not yet known. Search returns stable IDs and small summaries. Retrieval accepts those IDs and returns detail.

#### Fast search then authoritative confirmation

Example: BetaNYC Legistar.

Use when the live source is slow or search-poor. Local or cached search produces candidates. A live call confirms current status.

#### Configured multi-source primitives

Example: GTFS MCP.

Use when many publishers implement one standard. A manifest adds a publisher; tool contracts remain stable.

#### One core, several caller surfaces

Example: Imaging Data Commons.

Use for Commonwealth itself. Domain logic should not depend on MCP decorators, REST handlers, or CLI rendering.

#### Skills or resources for the correct walk

Example: Data Commons.

Use when a compact tool surface still requires ordered discovery, metadata inspection, and retrieval.

### 2. Findings

1. **nepa-mcp has a live GitHub Pages site** (`pnnl.github.io/nepa-mcp/`)
   plus a `docs/` folder (tool catalog, Map Composer docs, data-licensing
   notes). Its README leads with client-compatibility and stack badges and
   an embedded **screenshot of an interactive map** (Chesapeake Bay
   watershed, 12 overlay layers) demonstrating one tool in actual use, plus
   a structured table of all 20 servers with source-agency/purpose/auth
   columns.
2. **Power-Agent is Harvard SEAS-affiliated**, confirmed via its arXiv
   author affiliations; its project site (`power-agent.github.io`)
   redirects to a Harvard-hosted page (`poweragent.seas.harvard.edu`). The
   three repos (PowerMCP/PowerSkills/PowerAgentBench) each carry their own
   README rather than one unified site showing the tool→skill→benchmark
   flow visually — the layering is real (§ 4 of the reference evaluation
   still holds) but it is not demonstrated as an interactive flow anywhere
   public.
3. **civic-ai-tools has the strongest live demo of anything checked**:
   civicaitools.org runs genuinely interactive, rate-limited demos (NYC
   noise trends, 311 complaint comparisons, income by city) against real
   data, shows the **actual query the AI issued**, offers exportable
   Jupyter notebooks for reproducibility, and has an explicit "where the
   line is today" section separating built from planned features. Its
   whole pitch — signed, verifiable AI records — is the closest published
   analog to Commonwealth's provenance envelope found anywhere.
4. **github-mcp-server** has no GitHub Pages, no screenshots or diagrams —
   prose and JSON config docs only. Not a presentation model, despite being
   the flagship server by star count.
5. **fastmcp** (gofastmcp.com) and **modelcontextprotocol.io** are both
   polished, static documentation sites (animated hero, card-grid nav) —
   neither has a live in-browser tool-call demo on its homepage.

### 3. What this changed in the site

Of the checked projects, only civic-ai-tools ships a truly live, in-browser
interactive demo — nepa-mcp, Power-Agent, and github-mcp-server are all
static despite otherwise good docs. That gap, plus the direct request to
show "the calls, the APIs, what exactly is happening," is what
docs/index.html's Interactive demos section now targets, adapted to this
project's static-hosting constraint (no live query the way civic-ai-tools
has a server behind it):

- **Jurisdiction resolver playground** — every answer is precomputed by
  calling the real `JurisdictionTable.resolve()` at build time
  (`tools/build_site.py:build_resolver_demo`), never a JS reimplementation
  that could drift from the tool; locked by
  `test_resolver_demo_matches_the_live_resolver`.
- **Real HTTP exchanges on the audit trail** — the two calls that reach
  Fairfax County's live ArcGIS service now show the actual outbound URLs,
  params, and response shape (via `TrackingFetcher` wrapping the replay
  fetcher), not just the tool's own envelope. This is civic-ai-tools'
  "show the actual query" pattern, adapted to a recorded-fixture site
  instead of a live query console.
- **Jump-to-a-call nav** and a **coverage/warning decoder** cross-linking
  every dimension value and warning code to the real recorded call that
  demonstrates it — closer to nepa-mcp's "one screenshot per tool in
  action" than a bare glossary.

Not adopted: a separate marketing/demo domain (civic-ai-tools' own site is
off its README) — out of scope for a GitHub Pages site at this stage; a
unified tool→skill→benchmark flow diagram in Power-Agent's style — nothing
in Commonwealth yet has three layers to show (skills are still planned, per
docs/index.html's Skills section).

```bash
python3 tools/search_hn.py                 # HN stories + full comment threads
python3 tools/search_hn.py --ids 48592163  # specific threads
python3 tools/digest_hn_threads.py         # condense them into one digest

python3 tools/fetch_mcp_registry.py        # official registry snapshot
python3 tools/search_reddit.py             # blocked here; fails loud, see docstring

```

`research/notes/` holds the incremental output of the two research agents,
kept for provenance; the parts above supersede them.

### Known collection limits, verified 2026-08-26

- Reddit's JSON endpoints and the pullpush mirror return a bot challenge
  from this network. `search_reddit.py` supports `REDDIT_CLIENT_ID` /
  `REDDIT_CLIENT_SECRET` and works unauthenticated from most residential
  IPs. Until then, Reddit and X coverage comes from search snippets and is
  thinner than the HN material. Weigh it accordingly.
- The registry crawl caps at `--max-pages` (default 200 pages = 20,000
  servers). The 2026-08-26 snapshot hit that cap, so its total is a floor,
  and the digest says so.
- GitHub `in:readme` civic queries match large awesome-lists;
  `raw/github/civic_repos.json` needs filtering before use. Treat
  `matched_queries` and the description as the filter inputs.
