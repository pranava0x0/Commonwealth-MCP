## github/github-mcp-server

- Very active: 32.5k stars, 327 open issues, latest release v1.11.0 published 2026-08-25 (v1.10.x, v1.9.0, v1.8.0 all shipped within the prior month) — commits land daily. Source: `gh api repos/github/github-mcp-server` and `/releases`, 2026-08-26.
- **Material change vs. an older snapshot: an active, formalized tool-consolidation effort.** The repo now ships a `DeprecatedToolAliases` map (`pkg/github/deprecated_tool_aliases.go`) and a documented process (`docs/tool-renaming.md`) for collapsing many single-endpoint tools into fewer verb/"method"-dispatch tools while silently resolving old names for backward compatibility (works for both local `--tools` flags and remote `X-MCP-Tools` headers). Example: `get_workflow`, `get_workflow_job`, `get_workflow_job_logs`, `get_workflow_run`, `download_workflow_run_artifact` all now alias to one tool, `actions_get` (with a `method` string param selecting behavior). Same pattern for `actions_list`, `actions_run_trigger`, `issue_read`/`issue_write`, `pull_request_read`, `projects_get`/`projects_list`/`projects_write`, `label_write`. Currently 25 deprecated aliases are tracked. Source: raw `docs/tool-renaming.md` and README, github/github-mcp-server@main, fetched 2026-08-26.
- The consolidation is **partial, not total**: many domains are still one-tool-per-endpoint (e.g., gists has 4 separate tools `create_gist`/`get_gist`/`list_gists`/`update_gist`; dependabot, discussions, notifications, releases/tags/commits under `repos` are all still granular). Current total is 91 top-level tools across ~24 toolsets (`context`, `actions`, `code_quality`, `code_security`, `copilot`, `copilot_issue_intents`, `dependabot`, `discussions`, `gists`, `git`, `issues`, `labels`, `notifications`, `orgs`, `projects`, `pull_requests`, `repos`, `secret_protection`, `security_advisories`, `stargazers`, `users`, plus remote-only `copilot_spaces` and `github_support_docs_search`). Source: README tool listing, counted directly, 2026-08-26.
- Toolset selection mechanism unchanged in spirit but extended: `--toolsets`/`GITHUB_TOOLSETS` (or `all`/`default` specials) for coarse control, PLUS a newer fine-grained `--tools`/`GITHUB_TOOLS` flag that is additive with toolsets ("registers all tools from `repos` and `issues` toolsets, plus `get_gist`"). Source: README §"Specifying Toolsets"/"Using individual tools", 2026-08-26.
- Remote server (`https://api.githubcopilot.com/mcp/`) now exposes **per-toolset URLs** (`/x/<toolset>`) each with a `/readonly` variant, as an alternative to header-based config (`X-MCP-Toolsets`, `X-MCP-Tools`, `X-MCP-Readonly`). New header not previously documented: **`X-MCP-Lockdown`** — "enables lockdown mode, hiding public issue details created by users without push access... a best-effort content filter, not a security boundary" — i.e., a prompt-injection/content-trust mitigation baked into the remote server itself. Source: `docs/remote-server.md`, github/github-mcp-server@main, fetched 2026-08-26.
- Doc set also now includes `docs/scope-filtering.md`, `docs/policies-and-governance.md`, `docs/error-handling.md`, `docs/feature-flags.md`, `docs/host-integration.md`, `docs/insiders-features.md`, `docs/streamable-http.md`, `docs/testing.md`, `docs/github-app-auth.md`, `docs/oauth-login.md` — a much fuller operational-docs set than a typical reference server. Contents of these beyond titles not fetched (budget triage) — unverified in detail, filenames only confirmed via `gh api .../contents/docs`.
- **Architecture-doc implication**: the most-referenced production GitHub MCP server is actively moving toward "few semantic/method-dispatch tools" and provides a real, citable backward-compatibility mechanism (deprecation aliases) for doing so without breaking clients — directly relevant to Commonwealth-MCP's own tool-count/consolidation decisions.

## Cloudflare — cloudflare/mcp (Code Mode) and cloudflare/mcp-server-cloudflare

- **Cloudflare now runs two parallel, explicitly-documented MCP strategies, not one.** `cloudflare/mcp` (the "Code Mode" server, `https://mcp.cloudflare.com/mcp`) covers the *entire* Cloudflare API (~2,500 endpoints) through **3 tools total**: `docs` (search dev docs), `search` (write JS to query `spec.paths`), `execute` (write JS calling `cloudflare.request()`). `cloudflare/mcp-server-cloudflare` is a separate repo/collection of ~16 domain-specific servers (Workers Bindings, Observability, DNS Analytics, Radar, AI Gateway, etc.), each its own subdomain (`bindings.mcp.cloudflare.com`, `radar.mcp.cloudflare.com`, ...) with curated typed tools. The mcp-server-cloudflare README now states this explicitly as a fork-in-the-road: "Code Mode server... best when you want broad access... Domain-specific servers... best when you want curated, typed tools for a specific product area." Source: raw READMEs of both repos, fetched 2026-08-26.
- Quantified token cost table in the Code Mode README: native MCP with full schemas over the whole API = 2,594 tools / ~1.17M tokens (585% of a 200K context); native MCP with minimal/required-only schemas = 244K tokens (122% of context); Code Mode = 3 tools / ~1,100 tokens (0.5%). Source: `cloudflare/mcp` README table, 2026-08-26.
- Code Mode is not all-or-nothing: `?codemode=false` query param on the same MCP URL reverts to one-tool-per-endpoint (2,594 individual tools, e.g. `get_workers_scripts`, `post_d1_database`), explicitly for composability "if your MCP client already uses code mode, or you're composing this server with another server that uses code mode." Source: same README, 2026-08-26.
- Execution sandboxing detail (relevant to any server considering code-mode/execution tools): code runs via Cloudflare's **Dynamic Worker Loader API**, executing generated code in **isolated Workers** per the Code Mode pattern (not eval in the host process). Source: `cloudflare/mcp` README §"Build a Code Mode MCP Server", 2026-08-26.
- `cloudflare/mcp-server-cloudflare` (761/4,113 stars respectively — both very active, last push within a day of this survey) documents a transport migration: every domain server now exposes "the same stateless Streamable HTTP handler at `/mcp` and `/sse` through a fresh SDK v2 server factory"; a legacy `GET /sse` (old HTTP+SSE transport) now returns **410 Gone with a Problem Details body** pointing clients to migrate to `/mcp`. Source: `cloudflare/mcp-server-cloudflare` README intro, fetched 2026-08-26.
- Architecture-doc implication: this is a real vendor validating "few semantic tools via code execution" AND "many curated per-domain tools" as *coexisting, purpose-fit* strategies rather than one replacing the other — useful framing for Commonwealth-MCP if it ever debates a single code-mode gateway vs. several domain-scoped servers (e.g., per Virginia agency/dataset).

## PART B — New exemplars

## getsentry/sentry-mcp

- Production remote server at `https://mcp.sentry.dev` (also `/mcp` endpoint), built explicitly "as middleware to the upstream Sentry API, optimized for coding assistants like Cursor, Claude Code" — states plainly it is NOT a general-purpose Sentry API wrapper: "Our tool selection and priorities are focused on developer workflows and debugging use cases." Actively maintained (pushed same day as this survey, 828 stars, 103 open issues). Source: raw `README.md` + `gh api repos/getsentry/sentry-mcp`, getsentry/sentry-mcp@main, fetched 2026-08-26.
- **Tool design**: tools are grouped into named **"skills"** (e.g. `inspect`, `triage`, `seer`) above individual tool definitions (`skillDefinitions.ts/json` sit above `toolDefinitions.ts/json` in `packages/mcp-core/src`). Remote clients can select `?skills=inspect,triage` or exclude one with `?disable-skills=seer` (stdio equivalent: `--disable-skills=seer` / `MCP_DISABLE_SKILLS` env var). Tool source further organized by domain: `search-events`, `search-issue-events`, `search-issues`, `catalog`, `support`, `special`. AI-powered natural-language search tools (`search_events`, `search_issues`) require a configured LLM provider (OpenAI/Azure OpenAI/Anthropic/OpenRouter) to translate NL into Sentry's query syntax; without one, those specific tools are simply unavailable while the rest still work. Source: README + `gh api .../contents/packages/mcp-core/src`, 2026-08-26.
- **Auth model**: remote server supports standard MCP OAuth, but also a distinct pass-through mode — clients can send an upstream Sentry token directly via a custom `Sentry-Bearer` header (deliberately not `Bearer`, which is "reserved for MCP OAuth access tokens"); in that mode "the worker does not store, validate, exchange, or refresh the upstream token," it just forwards it, pushing token-lifetime responsibility to the client/upstream provider. Local/stdio mode uses a Sentry User Auth Token with explicit scopes (`org:read`, `project:read`, `project:write`, `team:read`, `team:write`, `event:write`). A Claude Code plugin (`getsentry/sentry-mcp` marketplace) installs a `sentry-mcp` subagent for automatic delegation, with a separate `sentry-mcp-experimental` variant for forward-looking tool changes. Source: README, 2026-08-26.
- **Repo layout**: pnpm/turborepo monorepo — `packages/mcp-core` (schemas, skills, tools, permissions), `packages/mcp-server` (the server), `packages/mcp-cloudflare` (Cloudflare Worker remote transport), `packages/mcp-server-evals` (LLM evals), `packages/mcp-server-mocks` (mocked upstream API), `packages/mcp-test-client` (custom CLI test client), `packages/smoke-tests`. Also ships `ast-grep-rules`/`ast-grep-rule-tests` (static-analysis lint rules enforced in CI) and an `openspec/` directory. Source: `gh api .../contents` and `/contents/packages`, 2026-08-26.
- **Test/demo structure — three distinct suites, explicitly documented**: (1) **Unit tests** (`pnpm test`, Vitest). (2) **Evaluations** (`pnpm eval`) using the **`vitest-evals`** package — LLM-graded eval tests that actually drive an LLM (via Vercel AI SDK — `ai`, `@ai-sdk/openai`, `@ai-sdk/mcp`) through the MCP tools, gated behind an `.env` with `OPENAI_API_KEY`/`OPENROUTER_API_KEY`; CI runs `eval:ci` which emits both JUnit XML and JSON result files. Upstream Sentry API calls are mocked with **MSW** (`mcp-server-mocks` package) so evals/units don't hit production Sentry. (3) **Manual testing** via a custom CLI (`pnpm -w run cli "who am I?"`, pointable at local dev, production `mcp.sentry.dev`, or stdio mode) — called "preferred for testing MCP changes" over the automated suites. Plus standard **MCP Inspector** support (`http://localhost:5173/mcp`) and two dedicated **testing playbooks**, `docs/testing/stdio.md` and `docs/testing/remote.md` (the latter explicitly covers OAuth, web UI, and CLI-client testing). Source: README §"Tests", `packages/mcp-server-evals/package.json`, fetched 2026-08-26.
- Architecture-doc implication: sentry-mcp is a strong worked example of (a) "skills" as a named grouping layer above tools with allow/deny-list query-param and CLI-flag control, (b) a clean separation between MCP-native OAuth and pass-through upstream-token auth, and (c) a three-tier test strategy (unit / LLM-graded eval / manual-preferred) that's more elaborate than most reference servers.

## Esri — MCP for ArcGIS Location Services

- **Esri's official offering is a closed, hosted beta service, not an open-source repo** — there is no single canonical Esri GitHub repository to study for tool-design patterns. The service is "MCP for ArcGIS Location Services," part of the ArcGIS Location Platform, in beta as of a June 2026 release; Esri invites feedback via an "Early Adopter Community" program. Source: WebSearch results and `developers.arcgis.com/ai-tools/mcp-arcgis-location-services/`, fetched 2026-08-26. (Esri's own arcgis-blog announcement post returned HTTP 403 to automated fetch — could not verify its exact wording directly; relying on the developer-docs page and search-result summaries instead.)
- **Connection**: server URL `https://location-services-mcp.arcgis.com/beta/mcp`. Auth is either an **API key as a `Bearer` token** in the `Authorization` header, or full **OAuth 2.0** user-authentication flow with dynamic token handling; an ArcGIS Location Platform or ArcGIS Online account is required either way. Documented client configs exist for Microsoft Copilot Studio, VS Code, Claude Desktop, Postman, Goose, and Kiro. Source: `developers.arcgis.com/ai-tools/mcp-arcgis-location-services/get-started/`, fetched 2026-08-26.
- **Tool design**: capabilities are described at a "geocoding, routing, elevation, and map generation" grain rather than as an exhaustive per-endpoint tool list — the docs name geocoding, routing/directions, elevation, static map generation, places search, GeoEnrichment, basemap styles/tiles, and a `map_with_overlay` tool, framed as broader functional capabilities rather than one tool per REST endpoint. No token-cost or tool-count table was found (unlike Cloudflare's Code Mode README) — the exact tool count is **unverified**. Source: same developer-docs pages, 2026-08-26.
- **The community/open-source landscape around ArcGIS + MCP is fragmented and explicitly unofficial.** Multiple independent projects exist with no clear dominant one: `arcgis-portal-mcp` (ArcGIS Portal/Online content search, feature-layer query/edit, user/group admin — its own docs state it is "not affiliated with, endorsed by, or sponsored by Esri Inc."), `eKerney/esri-mcp` (Esri Living Atlas / water-resources focus), `GarrickGarcia/ArcGISMCP`, `lwsinclair/arcgis-location-services-mcp`, `nicogis/MCP-Server-ArcGIS-Pro-AddIn` (ArcGIS Pro Add-In bridge), plus a `arcgis-mcp-server` PyPI package. None were vetted in depth here (budget triage) — treat all as **unverified** for quality/maturity; listed only to show the landscape is scattered, which is itself relevant context for Commonwealth-MCP as it is filling a gap rather than following one obvious open-source template. Source: WebSearch results, 2026-08-26.
- Architecture-doc implication: Commonwealth-MCP cannot borrow a proven open-source ArcGIS-wrapping architecture wholesale from Esri or the community — Esri's own answer is a closed hosted service with capability-level (not endpoint-level) tools, and the open-source field is a scatter of small, unaffiliated, unvetted projects. This strengthens the case for Commonwealth-MCP defining its own tool-grouping convention rather than copying an existing one.

## grafana/mcp-grafana

- Large, actively maintained: 3,390 stars, pushed 2026-08-25. A very long, thoroughly organized README (1,374 lines). Source: `gh api repos/grafana/mcp-grafana` + raw README, grafana/mcp-grafana@main, fetched 2026-08-26.

- Architecture-doc implication: supabase-mcp's two strongest transferable ideas are (1) DB-layer (not just tool-schema-layer) enforcement of read-only mode — defense in depth against a tool description being ignored or a schema bug — and (2) coupling project/tenant scoping directly to which tool groups are even registered, rather than relying on runtime checks inside each tool. Both map directly onto a Commonwealth-MCP concern (scoping by VA locality/agency, and guaranteeing read-only access to authoritative public data).

Source: raw README §"Version 2.0.0 breaking changes", 2026-08-26.
- **The actual "agent-first redesign" is documented in Notion's own blog post, "Notion's hosted MCP server: an inside look"** (notion.com/blog/notions-hosted-mcp-server-an-inside-look, published 2025-07-15 — predates this survey window but remains the canonical source; content not independently re-verified as unchanged since publication). Key claims from the post: Notion moved away from a 1:1 API-to-tool mapping because it "created suboptimal experiences for AI agents, like high-context token consumption from working with hierarchical block data in JSON," and because "the technical barrier was too high for widespread adoption." The hosted server instead exposes a curated blend of (a) new, ground-up **agent-oriented tools** designed for conversational use rather than rigid API semantics (named examples: `create-pages`, `update-page`, `search`) and (b) a smaller set of existing v1-API-wrapping tools with AI-friendly descriptions (example: `create-comment`). The `search` tool does semantic/natural-language search "surfacing pages across your Notion workspace plus over ten third-party connected apps." Source: WebFetch of the Notion blog post, 2026-08-26.
- **"Notion-flavored Markdown" replaces raw block JSON as the content representation**: the post describes "an enhanced 'Notion-flavored' Markdown spec, creating a powerful markup language tailored to Notion's broad set of blocks," chosen for "efficient content density per LLM token, requiring fewer tool interactions and less cost" while keeping feature parity with Notion's native block model. This is a concrete, named instance of the general "collapse a hierarchical/nested API resource into one dense text format a model can read and write directly" pattern. Source: same blog post, 2026-08-26.
- **Context-scoping tied to permissions**: per independent secondary summaries of the same material (not directly re-quoted from the primary post), an agent that only reads Notion pages "never gets write or delete tools loaded into its context" — i.e. tool visibility is trimmed per the granted permission level, explicitly framed as reducing both context consumption and "blast radius." Source: WebSearch summary citing the same Notion blog post, 2026-08-26 — this specific framing is **secondhand** (summarized by a search result, not directly quoted from the fetched page) and should be treated as slightly less certain than the directly-quoted material above.
- Architecture-doc implication: Notion is a clean, primary-source example of exactly the "many endpoint tools → few agent-workflow tools" transition Commonwealth-MCP might consider, with a named, motivated alternative content format (Notion-flavored Markdown) as the mechanism that made consolidation possible — worth citing specifically for the idea that consolidation often requires *also* redesigning the response/content format, not just merging tool signatures.

## OpenStreetMap / geospatial MCP servers

- No official/vendor server exists (OSM has no single corporate owner); the field is entirely community projects, and **`NERVsystems/osmmcp`** is the clear leader by star count (28 stars — small in absolute terms, but well ahead of a long tail of 0-3-star alternatives found in the same search: `tabibhasann/geo-mcp`, `chuofringer/placeroot` (Overture Maps, not OSM), `neco001/openstreetmap-mcp`, `danishashko/geocode-mcp`, `unmodeled-tyler/geospatial-context`, `BUZDOLAPCI/osm-tools`, `ni-c/osm-mcp`, `adelie-ai/openstreetmap-mcp` + `adelie-ai/geocode-mcp`, `pipeworx-io/mcp-nominatim`, `htristram/trustydata-mcp-server` (French address data specifically, hosted at mcp.trustydata.app)). Source: `gh api search/repositories`, 2026-08-26.
- **`NERVsystems/osmmcp` — a third, distinct tool-design philosophy worth naming alongside "few consolidated tools" and "many narrow endpoint tools": deliberately composable primitives.** The README has a dedicated "Composable Tool Design" section: "Many of our MCP tools are designed as composable primitives, enabling novel workflows that might not have been foreseen during development," with five explicit design principles — **uniform interfaces** (consistent parameter naming like `minLat`/`maxLon` across tools), **single responsibility** (each tool does one thing), **output/input compatibility** (one tool's output is directly usable as another's input), **functional independence** (no side effects/hidden dependencies), **precise error messages**. Documented example chains: `bbox_from_points → osm_query_bbox → filter_tags → sort_by_distance` (find POIs along a path); `centroid_points → find_nearby_places → filter_tags` (optimal meeting points); `route_fetch → polyline_decode → route_sample → filter_tags` (route analysis). The README frames the payoff explicitly: an LLM can compose "show the five closest wheelchair-accessible cafés that are open past 22:00 along my route" from primitives "without requiring custom server-side endpoints." Source: raw README §"Composable Tool Design", NERVsystems/osmmcp@main, fetched 2026-08-26.
- On top of the primitives sits a **second layer of curated composite/workflow tools** built from them: `find_nearby_places`, `suggest_meeting_point`, `explore_area`, `find_charging_stations`, `analyze_commute`, `analyze_neighborhood`, `find_schools_nearby`, `find_parking_facilities` — i.e. the same "primitives + workflow tools" duality seen elsewhere in this survey, but here both layers are exposed to the model simultaneously rather than the composite layer replacing the primitives. **25 tools total**, centrally defined in a single registry file (`pkg/tools/registry.go`) — the README states this registry-based design "makes it easy to add new tools without modifying multiple files." Source: README §"Implemented Tools" table and §"Project Structure", counted directly, 2026-08-26.
- **Production plumbing for a modest 28-star project**: `pkg/cache` (TTL-based caching of upstream API responses, 5-minute default — relevant given Nominatim/Overpass/OSRM all have strict public-usage rate-limit policies), `pkg/monitoring` (Prometheus metrics, health checking, connection monitoring), `pkg/tracing` (OpenTelemetry distributed tracing). **Test suite** (`go test ./...`): unit tests for polyline encoding/decoding, server integration tests, geographic-calculation tests, logging-utility tests, backed by a dedicated `pkg/testutil` helpers package. Source: README §"Project Structure"/"Testing", 2026-08-26.
- Architecture-doc implication: osmmcp's "composable primitives + curated composites, both exposed together" is a genuinely different third option from "collapse into few tools" (Cloudflare/Notion) and "many narrow endpoint tools" (CKAN/Grafana) — worth naming explicitly in the architecture doc's tool-design taxonomy, since it's specifically reasoned about (five named principles) rather than incidental. Its TTL-cache-in-front-of-rate-limited-public-APIs pattern is directly applicable to Commonwealth-MCP's own VA data sources.

## MCP gateway/aggregator landscape

- **`docker/mcp-registry`** (548 stars, pushed 2026-08-25) is "the Official Docker MCP Registry" — a curated catalog feeding three surfaces: the public [MCP Catalog](https://hub.docker.com/mcp), **Docker Desktop's MCP Toolkit**, and a `mcp` namespace on Docker Hub for Docker-built images. Every cataloged server runs in an isolated container regardless of submission type; the differentiator is submission method — "Docker-Built Image" entries get Docker's own build pipeline plus cryptographic signatures, provenance tracking, and SBOMs (Software Bills of Materials) and automatic security updates, while "Self-Provided Pre-Built Image" entries get container isolation only, without the enhanced supply-chain guarantees. All entries go through a review process before listing. Source: raw README, docker/mcp-registry@main, fetched 2026-08-26.
- **`IBM/mcp-context-forge`**, now branded **"ContextForge"** (4,367 stars, pushed 2026-08-25 — the most-starred gateway found in this survey), positions itself as "an open source registry and proxy that federates MCP, A2A, and REST/gRPC APIs with centralized governance, discovery, and observability." Four stated pillars: a **Tools Gateway** (MCP, REST, gRPC-to-MCP translation, plus a "TOON compression" feature — not independently verified what TOON stands for or does beyond the README's mention), an **Agent Gateway** (A2A protocol, OpenAI-compatible and Anthropic agent routing), an **API Gateway** (rate limiting, auth, retries, reverse proxy for plain REST services), and **Plugin Extensibility** (40+ plugins). Observability via OpenTelemetry with pluggable backends (Phoenix, Jaeger, Zipkin, other OTLP). Runs as a fully MCP-compliant server itself, distributed via PyPI (`mcp-contextforge-gateway`) or Docker/GHCR, and scales to multi-cluster Kubernetes with Redis-backed federation and caching. Source: raw README, IBM/mcp-context-forge@main, fetched 2026-08-26.
- **`obot-platform/obot`** ("Complete AI Governance Platform from Obot AI," 959 stars, pushed 2026-08-25) is the gateway underlying GSA-TTS/mcp-server-hub-catalog (see Part A). Explicitly multi-client, not tied to one AI product: "Desktop agents and tools such as Claude Code, Codex, Cursor, VS Code... can use the parts of the platform that apply to them." Core capabilities: an **MCP Gateway** as "a single governed entry point to every MCP server a user is allowed to reach" — proxies both Obot-hosted and externally-running MCP servers, can **compose new "composite" MCP servers that expose selected tools pulled from multiple underlying servers**, controls server/tool access by user or identity-provider group, manages MCP OAuth and credentials (including Kubernetes secret bindings), and supports **MCP or webhook filters that can inspect, reject, or modify MCP requests and responses in flight**; an **LLM Gateway** presenting provider-compatible endpoints; sandboxed execution for hosted servers/agents; a device-side component called **"Obot Sentry"** that scans/audits/enforces policy on local AI activity; and "MCP and Skills registries built on curated Git-backed catalogs" — the exact pattern GSA-TTS/mcp-server-hub-catalog follows (one YAML file per server), confirmed by the companion `obot-platform/mcp-catalog` repo (12 stars) that defines the entry format. Source: raw README, obot-platform/obot@main, and `gh api repos/obot-platform/mcp-catalog`, fetched 2026-08-26.
- **Discovery-only registries** (not gateways — no proxying/execution, just search-and-list), per WebSearch summaries of third-party comparison articles (not independently verified against each site directly): **Smithery** (smithery.ai) lets developers search, locally install via CLI, or run servers as Smithery-hosted remote endpoints; **Glama** (glama.ai/mcp) indexes the ecosystem with an in-browser MCP Inspector for pre-install testing and separately runs its own gateway (request logging, per-tool access control, managed OAuth, usage analytics) — one comparison piece cites Glama alone tracking "nearly 37,000 servers in mid-2026"; **PulseMCP** is described as "the largest hand-reviewed directory." One recurring practical recommendation across these comparison sources: submit a new server to four places for visibility — mcp.so, smithery.ai, glama.ai/mcp, and a PR against `punkpeye/awesome-mcp-servers`. Source: WebSearch of third-party review/comparison sites, 2026-08-26 — **this whole bullet is secondhand** (summarized by search results, not read directly from each registry's own site) and should be treated as directionally correct rather than precisely verified.
- Architecture-doc implication: three different gateway philosophies now exist at real scale — Docker's (container-isolation + supply-chain-security-first, consumer/desktop-oriented), IBM ContextForge's (protocol-federation + observability-first, enterprise/Kubernetes-oriented), and Obot's (governance + identity/policy-first, cross-client and now visibly adopted by a US federal agency via GSA-TTS). If Commonwealth-MCP ever wants distribution through a gateway rather than direct MCP-client configuration, Obot is the most concretely relevant given GSA's own adoption for adjacent (NEPA/environmental) government data servers.

## Test/demo structure patterns worth copying

Concrete, named, directly-transferable patterns observed in this survey, each attributed to its source repo (all sources as cited in the repo's own section above; fetched 2026-08-26):

1. **Uniform per-server test taxonomy — `pnnl/nepa-mcp`.** Every one of ~20 domain servers gets exactly the same 5 test files: `test_<server>_unit.py`, `_integration.py`, `_security.py`, `_resilience.py`, `_performance.py`. Cheap to apply to Commonwealth-MCP (which is also many servers, one per VA data source): pick the same 5 categories as a mandatory checklist per server, enforced by a repo-wide contract test (nepa-mcp's analog is `test_repo_health.py`/`test_tool_catalog.py`, which check that the catalog doc and registered servers stay in sync).
2. **Three-tier test strategy with LLM-graded evals — `getsentry/sentry-mcp`.** Unit tests (Vitest) + evaluations (`vitest-evals`, driving a real LLM through the MCP tools via the Vercel AI SDK, with CI emitting JUnit XML and JSON) + manual CLI testing explicitly documented as "preferred for testing MCP changes" over the automated tiers. Upstream API calls mocked with MSW so neither unit tests nor evals touch production. The eval tier is the most valuable and least commonly seen piece: it catches "the tool schema is technically correct but an LLM can't actually use it right," which unit tests structurally cannot catch.
3. **Hidden-grader agentic benchmark convention — `stripe/agent-toolkit`.** Each eval task is a standalone project with `environment/` (agent-visible starting state), `grader/` (hidden from the agent, run only after), and `solutions/` (hidden, used only to validate the benchmark itself). Scored best-of-3, with the winning transcript human-reviewed "for run integrity," published as a per-model leaderboard. This is the most rigorous pattern found for answering "can an agent actually get real work done with these tools," as opposed to "does the tool return the right JSON."
4. **Known-failures baseline + upstream reconciliation audit — `amurshak/congressMCP`.** A `KNOWN_FAILURES.md` baseline plus tests that assert against it, so new upstream-API breakage is distinguishable from already-cataloged quirks; a separate, dated, standing practice of re-auditing the wrapper against live upstream behavior (`documentation/upstream-reconciliation-audit-2026-08-21.md`) and a `tool-defect-register.md`. This is the single most relevant pattern for Commonwealth-MCP specifically, since it's designed for exactly Commonwealth-MCP's situation: a thin wrapper over third-party government data APIs of uneven reliability, where "is this failure new or expected" is a constant real question.
5. **In-memory transport + snapshot testing for fast iteration — `jlowin/fastmcp`.** Official documented pattern: wrap the server object directly in a test `Client(transport=mcp)` inside a pytest fixture — no subprocess, no real network, no separate MCP Inspector needed during development — combined with the `inline-snapshot` library for asserting complex tool-output structures (auto-filled/updated via `pytest --inline-snapshot=fix,create`) and `dirty-equals` for fuzzy assertions on non-deterministic fields. The lowest-friction pattern found for a tight server-development test loop.
6. **Schema-change snapshotting ("toolsnaps") + formal deprecation-alias process — `github/github-mcp-server`.** The contributor guide for renaming a tool explicitly lists "updating the tool registration, the tests and the toolsnaps" as one linked change, plus a `DeprecatedToolAliases` map so old tool names keep resolving after a rename. Snapshot-testing the tool *schemas themselves* (not just call outputs) catches accidental breaking changes to a tool's contract; the alias map makes intentional renames non-breaking for existing client configs.
7. **Runnable demo scripts against live data, zero-setup entry point — `npstorey/civic-ai-tools`.** An `examples/` directory of standalone scripts runnable via `uv run examples/<script>.py` against real live civic data (not mocked), plus a one-click GitHub Codespaces quick start ("nothing to install"). Optional API-key env vars degrade gracefully to lower rate limits rather than hard-failing. Good template for Commonwealth-MCP's own onboarding/demo story given it also wraps live public data.
8. **MCP Inspector as the common baseline, everywhere.** Every actively-maintained server surveyed that documented a dev workflow at all (sentry-mcp, github-mcp-server via `docs/testing.md`, fastmcp implicitly) pointed to the standard `@modelcontextprotocol/inspector` as the manual-verification tool of first resort, layered underneath whatever project-specific automation exists. Worth treating as the non-negotiable minimum for Commonwealth-MCP regardless of what else is built.

**Strongest three for a from-scratch adoption priority**: pattern 1 (nepa-mcp's uniform per-server taxonomy — closest domain analog, trivial to adopt), pattern 4 (congressMCP's known-failures/reconciliation-audit practice — most directly addresses Commonwealth-MCP's actual failure mode, unreliable government upstreams), and pattern 3 (Stripe's hidden-grader benchmark convention — the most rigorous answer to "do the tools actually work for an agent," if Commonwealth-MCP ever builds an eval suite beyond unit tests).
